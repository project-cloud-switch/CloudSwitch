# Обсуждение реализации общего хранения

**Начальная схема, общие правила создания заданий, outbox и владение миграциями реализованы.** См. [решения API v1](../decisions/api-v1.md), `CloudSwitch.Persistence` и `src/CloudSwitch.Persistence/DatabasePermissions.sql`. Предлагаемые рецензенты — Полина, Влад и Егор. Связанная задача [#2](https://github.com/project-cloud-switch/CloudSwitch/issues/2). Ниже сохранены исходные вопросы как контекст обсуждения.

## Согласовано

API и Worker используют общую PostgreSQL. API владеет конфигурацией и создаёт ручные задания. Doctor владеет здоровьем и инцидентами и создаёт автоматические задания. Deployer владеет состоянием выполнения и активным окружением. API читает прогресс напрямую. Notifications владеет собственным состоянием доставки.

## Необходимо решить

- Минимальные таблицы и столбцы конфигурации, активного окружения, заданий, инцидентов и outbox в соответствии с согласованными снимками сообщений.
- Как API и Doctor применяют одинаковые ограничения создания заданий без дублирования несовместимых правил. Какой проект владеет общей схемой и миграциями?
- Как обеспечить одну активную миграцию на развёртывание, уникальность автоматических заданий инцидента и идемпотентность ручных запросов.
- Границы транзакций создания инцидента и задания, сохранения прогресса и обновления активной цели.
- Права БД и запуск единого согласованного процесса миграций локально и в CI.

Доставка конфигурации Doctor и распределение проверок между репликами рассматриваются [отдельно](doctor-configuration.md). Отдельные очереди реплик и аренды мониторинга заранее не предполагаются.

## Результат встречи

Минимальный план схемы, ответственный за миграции, границы транзакций и записи. Реализация БД во время встречи не требуется.

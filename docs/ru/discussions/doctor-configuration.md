# Обсуждение конфигурации Doctor и реплик

**Выбран начальный механизм получения конфигурации — загрузка PostgreSQL при запуске и опрос ревизий.** См. [решения API v1](../decisions/api-v1.md). Событийное распространение и координация реплик отложены. Ниже сохранены исходные варианты для будущего рассмотрения.

## Вопрос

Как Doctor должен получать изменения конфигурации и возобновлять мониторинг после перезапуска, сохраняя простоту первой реализации?

API владеет конфигурацией в PostgreSQL. Событие конфигурации API рассматривается как предпочтительное направление. Обновления должны доходить до каждого Doctor, которому они нужны.

## Контракт конфигурации

- Передавать полный снимок или ссылку на развёртывание и конфигурацию, которую Doctor читает из PostgreSQL?
- Какие сведения о ревизии и включении/отключении нужны? Как обрабатывать удаление и перезапуск?
- Как Doctor узнаёт новый активный endpoint после переключения?

Контракт можно согласовать до выбора будущей схемы с несколькими репликами. Предлагаемые рецензенты — Полина и Влад. Связанные задачи [#2](https://github.com/project-cloud-switch/CloudSwitch/issues/2) и [#14](https://github.com/project-cloud-switch/CloudSwitch/issues/14).

## Варианты для сравнения

- Начать с одной реплики Worker и событийной конфигурации Doctor. Вернуться к координации при масштабировании.
- Рассылать обновления всем репликам Doctor с отдельной подпиской каждой и снимком БД при запуске. Отдельно решить, проверяют ли все реплики или делят ответственность.
- Использовать общий планировщик Doctor, распределяющий проверки между репликами Worker вместо отдельных расписаний каждой реплики.

Последнее предложение добавляло временные очереди, объединение снимков и событий, маркеры удаления и аренды мониторинга. Его можно пересмотреть в будущем.

## Необходимые гарантии

- Изменения конфигурации, отключение, удаление и перезапуски обрабатываются корректно.
- Устаревшие наблюдения не запускают восстановление со старыми настройками.
- Повторные наблюдения и сообщения не создают дубли инцидентов или миграций.

Выбрать минимальный подход, соответствующий текущим требованиям развёртывания, прежде чем добавлять контракты конфигурации или инфраструктуру реплик.

## Результат встречи

Выбрать начальный состав обновления, механизм доставки и восстановления после перезапуска. Зафиксировать отложенные вопросы масштабирования реплик и статус каждого предлагаемого механизма.

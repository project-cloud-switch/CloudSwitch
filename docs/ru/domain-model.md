# Модель миграции

Согласованный проект для [#2](https://github.com/project-cloud-switch/CloudSwitch/issues/2). Общие сущности, миграции и надёжное создание заданий реализованы в `CloudSwitch.Persistence`. См. [решения API v1](decisions/api-v1.md). Worker использует постоянные аренды выполнения, сохранение прогресса и транзакционный outbox с явно включаемыми локальными адаптерами симуляции. Реальное облачное выполнение и мониторинг Doctor ожидают реализации.

Доменные модели находятся в `src/CloudSwitch.Persistence/Domain` общего проекта. Сущности инкапсулируют создание, изменение конфигурации, ревизии и удаление. Объекты конфигурации хранят неизменяемые копии входных данных. Обязательное состояние инициализируется конструкторами, необязательное явно допускает null. MVC-контроллеры используют DTO запросов и ответов и вызывают прикладные сервисы. Репозитории и EF-маппинги отвечают за хранение. Интеграционные сообщения создаются явным преобразованием контрактов.

## Объём разработки

Спринт 2 предусматривает мониторинг stateless-контейнера в Yandex Cloud и ручную либо автоматическую миграцию в одно резервное облако по политике восстановления. Последовательность — создание инфраструктуры, проверка здоровья, переключение трафика и проверка точки входа. При недоступности источника используется сохранённая конфигурация приложения.

Используется Terraform. OpenTofu, миграция БД и томов, автоматический возврат и удаление источника отложены. Локальная симуляция поддерживает CI, демонстрация использует реальные облака. CloudSwitch, PostgreSQL и RabbitMQ размещаются вне области отказа источника. Доступ к образам и управлению трафиком также должен сохраняться при сбое.

## Общая модель PostgreSQL

| Запись | Назначение | Владелец записи |
| --- | --- | --- |
| User | Внешняя идентичность и владение ресурсами. | API |
| Deployment | Конфигурация приложения, политика мониторинга и восстановления, точка входа, ревизия конфигурации. | API |
| TargetConfiguration | Разрешённые параметры провайдера и модуля, ссылки на секреты. | API |
| DeploymentRuntime | Активный провайдер, endpoint и ревизия. Сначала зарегистрированный источник, затем проверенное целевое окружение. | Worker |
| Job | Неизменяемый снимок запроса, причина запуска, необязательный инцидент, состояние, фаза, попытки, аренда, контрольные точки и результаты. | API/Doctor создают, Deployer обновляет выполнение. |
| JobEvent | Упорядоченный прогресс с ID события, корреляцией и безопасным результатом. | Deployer |
| HealthObservation / Incident | Счётчики проверок, здоровье, последовательность и эпизод сбоя отдельно от заданий. | Doctor |

API читает состояние заданий и здоровья напрямую. Worker инициализирует активное окружение по регистрации. Doctor использует настройки API и endpoint активного окружения, отбрасывая результаты для устаревших настроек или адресов. Notifications владеет состоянием доставки и дедупликации. Сохраняются ссылки на секреты.

Начальный механизм обнаружения конфигурации Doctor читает активные настройки PostgreSQL при запуске и опрашивает ревизии. Событийная доставка и распределение проверок между репликами отложены. Дополнительная таблица аренд мониторинга не требуется. См. [решения API v1](decisions/api-v1.md).

## Реакция на сбой

Doctor подтверждает сбой и восстановление порогами последовательных проверок и публикует `DeploymentHealthChanged` через outbox. `Unknown` не запускает восстановление.

Notifications уведомляет владельца. В `NotifyOnly` автоматическое задание не создаётся. В `Automatic` Doctor внутри транзакции создания задания проверяет текущую политику, здоровье и активного провайдера, сохраняет одно задание на инцидент и публикует `DeploymentRequested`. API использует те же правила для ручных запросов.

После проверенного переключения Deployer записывает новое активное окружение, которое затем проверяет Doctor. Повторные проверки не должны запускать бесконечные миграции после неудачного задания.

## Жизненный цикл задания и ограничения

`Pending → Running → Succeeded или Failed`

Deployer выполняет **создание инфраструктуры → проверку целевого приложения → переключение трафика → проверку точки входа**. Succeeded требует проверки здоровья и трафика. Неудачная проверка здоровья блокирует переключение. При сбое сохраняются контрольные точки и наблюдаемое состояние инфраструктуры и маршрутизации. Источник сохраняется.

- Одна активная миграция на развёртывание для API и Doctor.
- Уникальная пара `(DeploymentId, IncidentId)` для автоматических заданий. Повтор ручного ключа возвращает исходное задание.
- Только текущий владелец аренды обновляет выполнение. Число попыток ограничивается, устаревшие исполнители блокируются механизмом fencing.
- Задания с истёкшей арендой восстанавливаются из контрольных точек. Перед повтором внешних операций сверяется фактическое состояние инфраструктуры и маршрутизации.
- Состояние Terraform целевого окружения переиспользуется между попытками и хранится отдельно от состояния источника.
- Состояние и исходящие сообщения сохраняются атомарно через outbox. Используются уникальные ID событий и `(JobId, Sequence)`, индексы состояния и срока аренды.

Используются разные роли БД для API и Worker и один согласованный процесс миграции схемы. См. [архитектуру](architecture.md), [#5 — выполнение](https://github.com/project-cloud-switch/CloudSwitch/issues/5), [#7 — восстановление](https://github.com/project-cloud-switch/CloudSwitch/issues/7), [#12 — здоровье цели](https://github.com/project-cloud-switch/CloudSwitch/issues/12) и [#14 — Doctor](https://github.com/project-cloud-switch/CloudSwitch/issues/14).

# Мониторинг источника и реакция на подтверждённый сбой (часть API)

## 1. Суть задачи в целом

Doctor (часть Worker) периодически проверяет здоровье зарегистрированного приложения снаружи облака-источника. После нескольких подряд неудачных проверок он:
- открывает один инцидент и публикует `DeploymentHealthChanged`;
- в режиме `NotifyOnly` (по умолчанию) только оповещает владельца;
- в режиме `Automatic` сам создаёт job и публикует `DeploymentRequested` по тем же правилам, что и API.

Одна единичная ошибка проверки и статус `Unknown` миграцию не запускают. Упавший endpoint означает «приложение недоступно», а не «упал весь провайдер». Автоматического failback нет.

## 2. Какая часть моя

Doctor, Deployer и уведомления я не пишу. На мне:

1. **Хранение и валидация настроек мониторинга** (в рамках #4): `DeploymentMonitoringConfiguration`, `HealthCheckPolicy`, `RecoveryPolicy`.
2. **Проверка владельца** для настроек, health и уведомлений об инцидентах (в рамках #3).
3. **Чтение health через REST** (`GET /deployments/{id}/health`) из данных, которые пишет Doctor.
4. **Общие правила создания job** для API и Doctor: одна активная миграция на деплоймент, один автоматический job на `(DeploymentId, IncidentId)`.

## 3. Предлагаемое решение

**Что хранит API.** Настройки мониторинга лежат в PostgreSQL (владелец записи API): провайдер, endpoint, `HealthCheckPolicy`, `RecoveryPolicy`. Добавить номер ревизии настроек, чтобы Doctor мог отбрасывать наблюдения по устаревшим настройкам или endpoint (так сказано в `domain-model.md`).

**Валидация** (по `contracts.md` и issue):
- `intervalSeconds`, `timeoutSeconds`, `failureThreshold`, `recoveryThreshold`: положительные, с разумными верхними границами;
- `path` начинается с `/`, без символов, ломающих URL;
- `endpoint`: только разрешённый HTTP(S), без loopback и приватных адресов (защита от SSRF);
- `RecoveryPolicy`: по умолчанию `NotifyOnly`, `Automatic` только с `TargetConfigurationId`, принадлежащим пользователю.

**Как настройки попадают к Doctor** (открыто, нужно решение Влада и Егора). Два варианта:
- **A. Doctor читает таблицу настроек из БД** (периодически или при перезапуске) и смотрит на ревизию. Минимум нового: нет новых событий и очередей, как и требует issue (без лишних очередей и leases).
- **B. API публикует событие `DeploymentMonitoringConfigurationChanged`.** Это «предпочтительное направление» в `architecture.md`, но схему и доставку на несколько реплик ещё надо проектировать.

Для Спринта 2 я предлагаю начать с A и добавить B, если команда решит иначе.

**Общие правила создания job.** Ограничения лучше держать в БД: частичный уникальный индекс на активные job по деплойменту и уникальность `(DeploymentId, IncidentId)`. Тогда и API, и Doctor подчиняются им одинаково, а правила не дублируются кодом. Нужен договор, где живёт общий код (в `CloudSwitch.Contracts` бизнес-логики быть не должно).

**Health через REST.** API читает `HealthObservation` и `Incident` напрямую из БД; формат ответа описан в `api-contracts.md`, раздел 2.5.

**Порядок работы** (после #3 и #4):
1. Сущность и таблица настроек мониторинга с ревизией.
2. Эндпоинты создания и изменения настроек с валидацией.
3. Ограничения уникальности для job.
4. `GET .../health`.
5. Тесты: валидация, `NotifyOnly` по умолчанию, `Automatic` без доступа, чужой деплоймент.

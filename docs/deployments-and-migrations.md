# Регистрация деплойментов и отправка миграций

Зависит от #2 (контракты) и #3 (авторизация). Результат использует #5 (Deployer) и #9 (уведомления).

## 1. Суть задачи

API должен позволять пользователю:
1. Зарегистрировать приложение (stateless-контейнер в Яндексе) со всеми настройками, нужными, чтобы поднять его в другом облаке.
2. Запустить миграцию на резервное облако вручную.
3. Смотреть ход миграции.

Главное требование: миграция должна запускаться, даже если Яндекс уже лежит. Поэтому всё нужное API сохраняет заранее и в момент запуска копирует в снапшот, ничего не спрашивая у источника.

Что API НЕ делает: не запускает Terraform (это Deployer), не мониторит здоровье (это Doctor), не рассылает уведомления (это Notifications), не мигрирует базы и диски, не удаляет источник, не делает автоматический failback.

## 2. Что нужно сделать (по issue)

- CRUD зарегистрированных деплойментов: образ, настройки, личность исходного Yandex-деплоймента, утверждённая резервная конфигурация, health-политика, домен входа.
- Эндпоинт отправки миграции с выбором резервного провайдера.
- Снапшот на момент отправки: проверить и сохранить, а не брать данные из упавшего источника.
- Публикация `DeploymentRequested` через MassTransit с transactional outbox.
- Хранение и чтение job: статус, попытки, фаза, endpoint цели, безопасные ошибки.
- Ключ идемпотентности и запрет конфликтующих активных миграций для одного деплоймента или домена.
- Сохранение и проверка `DeploymentMonitoringConfiguration` (`HealthCheckPolicy`, `RecoveryPolicy`).
- OpenAPI, тесты на владение и валидацию.

## 3. Предлагаемое решение

Ниже мои предложения, а не решения команды. Спорные места вынесены в раздел 4.

**Стек.** ASP.NET Core, EF Core с PostgreSQL, MassTransit с EF Core outbox, Swashbuckle или встроенный OpenAPI.

**Сущности API** (из `domain-model.md`): `User`, `Deployment`, `TargetConfiguration`, `Job`, таблицы outbox и ключей идемпотентности. `DeploymentRuntime` создаёт API при регистрации, дальше его обновляет Worker.

**Эндпоинты:** см. `api-contracts.md`, раздел 2 (регистрация, миграция, `jobs/{id}`, `jobs/current`, `health`).

**Отправка миграции (одна транзакция):**
1. Проверить владельца и права на целевую конфигурацию.
2. Проверить идемпотентность (ключ плюс хэш тела запроса).
3. Проверить, что активной миграции нет.
4. Собрать `DeploymentSpecification` из сохранённой конфигурации и записать job (`Pending`) со снапшотом.
5. Положить `DeploymentRequested` в outbox.
6. Закоммитить; MassTransit отправит событие в RabbitMQ, даже если процесс упадёт после коммита.

**Идемпотентность:** таблица с уникальным индексом `(UserId, DeploymentId, IdempotencyKey)`, где хранятся хэш тела и `JobId`. Тот же ключ и то же тело возвращает ту же job (`200`), тот же ключ и другое тело возвращает `409`. Либо же без отедельной таблицы поля добавить в другую и парно свзать

**Запрет параллельных миграций:** частичный уникальный индекс в БД на `Job(DeploymentId)` для статусов `Pending` и `Running`. Тогда запрет работает при любой гонке, и Doctor подчиняется ему же. Аналогичное ограничение нужно и по домену входа.

**Снапшот:** `DeploymentRequested.Specification` собирается один раз и хранится в job неизменяемым. Изменения настроек во время миграции её не затрагивают.

**Валидация и отказы:** неподдерживаемый провайдер, образ без `@sha256:`, требование постоянного хранилища (stateful), секреты не ссылкой, а значением.

**Чтение статуса:** API читает job и health напрямую из PostgreSQL. Статус и фазу пишет Deployer. События статуса API применять не обязан, если проекция не нужна.

**Идентификаторы (предложение тимлида):** внутри и в событиях остаются `Guid`, а в REST выводятся с префиксом: `job-`, `dep-`, `tcfg-`, `inc-`. Проверка при вводе: префикс должен соответствовать типу.

**Порядок работы:**
1. Сущности и схема БД, согласованная с Егором.
2. Регистрация деплоймента и целевой конфигурации.
3. Отправка миграции со снапшотом и outbox.
4. Идемпотентность и уникальные индексы.
5. Чтение job и health.
6. Конфигурация мониторинга.
7. OpenAPI.
8. Тесты: владение, валидация, идемпотентность, гонки, сбой процесса между записью и публикацией.

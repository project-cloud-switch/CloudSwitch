# Авторизация операций с деплойментами и миграциями

## 1. Суть задачи

Сделать так, чтобы:
- без входа в систему API ничего не отдавал (`401`);
- пользователь видел и запускал только свои деплойменты, job и конфигурации;
- нельзя получить чужие данные, подставив чужой id или чужую ссылку на секрет;
- секреты нигде не светились: ни в ответах, ни в сообщениях, ни в логах;
- ошибки возвращались в одном безопасном формате.

## 2. Что нужно сделать (по issue)

- JWT-аутентификация, валидация ввода, глобальная обработка исключений.
- Проверка владельца для деплойментов, миграций, job и ссылок на credentials и конфигурации.
- Проверка доступа и к исходной регистрации, и к выбранной целевой конфигурации и домену.
- Отклонение недопустимых сочетаний провайдеров и stateful-конфигураций.
- Только владелец деплоймента может настраивать endpoint мониторинга и включать `Automatic` с утверждённой целевой конфигурацией. Те же правила для health и уведомлений об инцидентах.
- Интеграционные тесты: вход, владение, доступ другого пользователя.

## 3. Предлагаемое решение

**Вход.** По совету тимлида токены выдаёт готовый identity provider (IdP), а API только проверяет JWT: подпись, издателя, аудиторию и срок. Идентификатор пользователя берётся из claim `sub` и превращается в `UserId`. Так API не хранит пароли и не выдаёт токены.

Варианты IdP: Keycloak (самый распространённый, в Docker), ZITADEL, Authentik, облачный сервис. Выбор за командой (вопросы 1–3).

**Проверка владельца.** Один общий механизм, чтобы не повторять его в каждом эндпоинте:
- каждый запрос к данным фильтруется по `UserId`;
- чужой или несуществующий ресурс отдаёт `404`, а не `403`, чтобы не раскрывать существование;
- при отправке миграции проверяется владение и деплойментом, и целевой конфигурацией;
- при `recovery.mode = Automatic` проверяется, что `targetConfigurationId` принадлежит этому пользователю.

**Ссылки на секреты.** Простое правило: ссылка вида `vault://cloudswitch/users/{userId}/...` допустима, только если `{userId}` совпадает с пользователем из токена. Чужую ссылку нельзя подставить, и проверка не требует обращения в Vault. Это моё предложение, его нужно подтвердить (вопрос 6).

**Ошибки.** Единая обработка в формате `application/problem+json` с полями `code` и `traceId`. Без стек-трейсов, сырых ответов провайдера и секретов.

**Логи.** Не писать тела запросов с `secretReferences` и заголовок `Authorization`.

**Валидация.** Ограничения на провайдеров, `image` с дайджестом, `endpoint` (только допустимый HTTPS, без приватных адресов), закрытые списки значений.

**Тесты.** `WebApplicationFactory` с тестовым обработчиком аутентификации (без настоящего IdP): запрос без токена, запрос другого пользователя к чужому деплойменту, job и целевой конфигурации, чужая ссылка на секрет, проверка отсутствия секретов в ответах.

**Порядок работы:**
1. Договориться об IdP и формате `sub`.
2. Подключить JwtBearer и политику «нужен вход».
3. Общий механизм проверки владельца.
4. Глобальная обработка ошибок.
5. Проверка ссылок на секреты.
6. Тесты.

## 4. Что вне объёма

Регистрация пользователей, пароли, восстановление доступа и выдача токенов, если выбран готовый IdP. Авторизация подписок SignalR (#8).
